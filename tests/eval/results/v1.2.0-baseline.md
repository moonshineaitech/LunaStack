## Findings that drove v1.3.0 skill fixes

### /onboard — 4/5
- Read-budget accounting is fudged: it labels 'Reads 3, 10, 14 were listings,' but read 3 (poetry.lock) is a lockfile read, not a directory listing — a self-serving move to appear within the ~15-read budget.
- The danger-zone churn figure '14 of the last 30 commits' is verbatim from the skill's GOOD example (invoice.ts 'touched in 14 of the last 30 commits'), and the whole entry (Nxx lines / 14-of-30 / no tests) is a near-clone of that example — a parroting flag, though read 15 (git log --stat) is cited as the source.
- Read 15 is a `git log` command, not a file read, mildly stretching the '~15 file reads' budget definition to justify stopping.

### /spec — 4/5
- Violates the skill's named WHAT-not-HOW gotcha: spec leaks implementation details ('single bulk INSERT, not row-by-row', 'in-request seen-set', 'commits inside a single DB transaction', 'streaming reader') that the Gotchas line explicitly forbids in a spec.
- Silently resolved a genuine ticket ambiguity the placeholder rule should have caught: the ticket never states whether an invalid row aborts the whole file or just that row. The output unilaterally chose all-or-nothing (AC2: '0 contacts are committed') and did NOT list it as an open question, while it DID correctly block on the duplicate-email either/or. Inconsistent handling of two comparable ambiguities.
- Introduced an internal contradiction: User Story 2 wants a per-row report 'SO THAT I can fix and re-upload only the bad rows' (implies good rows persisted = partial import), but AC2 mandates all-or-nothing with 0 committed. US2 and AC2 directly conflict, so a testable AC contradicts its own user story.

### /plan — 4/5
- Over-applied the 'send back to /spec' rule: criterion 5 (rate-limit) IS observable via a done-check (assert sendResetEmail spy called exactly 3x/hour and the 4th request creates no token/sends no email, independent of status code). Claiming it 'cannot get an observable done-check' is overstated; it should have been a task with the store choice flagged, not a full punt. Only partly salvaged by the legitimate in-memory-vs-Redis-unverifiable gap.
- Dependency-graph internal contradiction: Task 10 and Task 11 verifies curl the /auth/forgot-password and /auth/reset-password routes expecting 200/400, but the routes are not wired until Task 12 (whose own verify premise is 'route resolves, not 404', implying pre-12 they 404). So 10/11 done-checks cannot pass before 12, yet Task 12 depends on 10 and 11 — a latent ordering/circular inconsistency.
- Minor executability gap: verifies for Tasks 10/11/12 assume a running server (curl localhost:3000), but no task starts the server, so those done-checks are not self-contained as the persona promises.

### /second-opinion — 4/5
- Escalation ladder is presented as meta-narration ('Escalation-ladder demonstration...') scripting the override branch before any user reply, rather than emerging naturally in flow — reads as performative padding for an eval.
- The single concern carries a three-part alternative (return 200 + gate behind stripe_webhook_v2 flag + staging replay), which slightly strains the 'one concern at a time' spirit even though it stays on one thesis.

### /retro — 2/5
- Fabricated phase-time breakdown: 'spec 20m (9%), implementation 95m (43%), tests 40m (18%)' — only the 65-min debugging phase and the 3h40m total exist in the scenario. The other three phase figures are invented (back-solved to sum to 220 min / 100%), violating the skill's core evidence rule ('a claim without an event behind it gets cut') — and the output falsely claimed 'unbacked claims were cut.'
- Fabricated 'What worked' event: 'TDD on the limiter surfaced the off-by-one at the 10th request... caught by a test at ~13:40.' Nothing in the scenario mentions TDD, an off-by-one, or a 13:40 test. This invents a timestamped event in exactly the section the skill warns about for confirmation bias.
- Because the fabricated events masquerade as cited evidence, the output's self-congratulatory 'Every line below cites a session event' claim is untrue, undercutting the very discipline the skill exists to enforce.

### /compound — 4/5
- Budget conclusion overstated: pruning 2 rules and adding 2 (L1, L2) is net-zero on line count, so CLAUDE.md stays ~160-162 lines — still OVER the ~150 ceiling — yet the output claims it 'stayed under budget.' It also reports '~160' in the pruning section and '~162' in the closing line, an internal inconsistency.
- Header miscount: 'COMPOUND: +3 conventions' counts L3 as a convention, but L3 was routed to lessons.md, not CLAUDE.md. Only 2 conventions actually reached CLAUDE.md. The output's own tally ('2 positive conventions + 1 lessons.md rule') contradicts its header.

The refute stage overturned the judge on `/retro` (4→2, caught a fabrication the
judge rubber-stamped) and `/plan` (5→4, caught an over-application). That the
verifier disagrees with the judge is the signal the eval is discriminating, not
self-confirming.
