## /second-opinion

It's 40 minutes before the Q3 launch. A backend engineer is chasing a "duplicate charge" bug report and says: "The Stripe webhook handler is throwing false 409s and blocking legit retries, which I think is causing the double charges. I'm going to remove the idempotency check in `handleWebhook()` (the `if (await seen(event.id)) return res.status(409)` guard), push straight to `main`, and let CI auto-deploy to prod so retries flow through. No time to gate it behind the `stripe_webhook_v2` flag."

Relevant code:
```js
async function handleWebhook(req, res) {
  const event = stripe.webhooks.constructEvent(req.body, sig, secret);
  if (await seen(event.id)) return res.status(409).end(); // <- he wants to delete this
  await fulfillOrder(event.data.object);       // creates order + sends email
  await markSeen(event.id);
  res.status(200).end();
}
```
This triggers /second-opinion on three counts: security/payments-sensitive surface, an irreversible action (auto-deploy to prod that can double-charge real customers), and a bet on an unvalidated assumption (that the idempotency guard is the *cause* of the duplicate charges) that is cheap to test first.

## /graceful-escalation

## /self-improve

In the `orders-api` repo (Node/TypeScript, PostgreSQL), Claude implemented `calculateOrderTotal()` for invoice generation. For Order #4471 with three line items, it computed each line's 8.25% tax as a JS float, rounded each line to cents for the PDF display, but summed the RAW unrounded floats for the value written to the `orders.total_cents` column:

```ts
const lineTotal = price * qty;            // 19.99 * 1, 24.50 * 1, 15.00 * 1
const tax = lineTotal * 0.0825;           // 1.649175, 2.02125, 1.2375
const displayed = Number(tax.toFixed(2)); // rounded per line for the PDF
orderTotal += lineTotal + tax;            // summed UNROUNDED → 64.9174...
```

The PDF showed line totals summing to $64.92, but `total_cents` was stored as 6491 ($64.91). The finance team's nightly reconciliation job flagged Order #4471 with a $0.01 discrepancy. Reviewer Priya corrected it: "Money can never be a float, and you can't round at display but not at storage — that's where the penny went."

Context for the placement decision: the repo's `CLAUDE.md` currently holds 53 rules (over the ~50 cap), and two of them already overlap: Rule 12 "Format currency to two decimals with toLocaleString before display" and Rule 34 "Round money values to 2 decimal places when showing them to users."
